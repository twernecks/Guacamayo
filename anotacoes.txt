Crie a constituição inicial deste projeto.

Contexto:
O produto começa como um frontend em React, inicialmente uma landing page institucional para uma pousada. No futuro, ele evoluirá para uma aplicação web/SaaS com backend, APIs, 
autenticação e regras de negócio. A constituição deve orientar decisões presentes sem impedir essa evolução.

Objetivo inicial:
Criar uma landing page de alta qualidade para divulgar a pousada, seus quartos, comodidades, localização e o serviço de locação de espaços para casamentos e eventos. 
O site terá conteúdo visual, galerias de fotos, chamadas para reserva/contato e boa experiência em dispositivos móveis.

Defina princípios obrigatórios, claros, verificáveis e com justificativa, cobrindo:

1. Frontend React moderno
   - Usar React com TypeScript.
   - Priorizar componentes pequenos, reutilizáveis, acessíveis e orientados ao domínio.
   - Separar componentes visuais, páginas/seções, hooks, serviços e tipos.
   - Evitar componentes excessivamente grandes e lógica de negócio acoplada à interface.

2. Estado e dados
   - Manter estado local quando possível.
   - Introduzir estado global apenas quando houver necessidade real e documentada.
   - Preparar uma camada de serviços/repositórios para que dados inicialmente estáticos possam ser substituídos futuramente por APIs sem reescrever a interface.
   - Não implementar backend nesta fase.

3. Qualidade e manutenção
   - TypeScript estrito, lint, formatação automática e convenções consistentes.
   - Testes proporcionais ao risco: lógica crítica, componentes interativos e fluxos de conversão devem ser testáveis.
   - Revisões devem avaliar acessibilidade, responsividade, performance, segurança básica e legibilidade.

4. UX, design e conteúdo
   - Mobile-first, responsivo e acessível conforme WCAG AA.
   - Foco em conversão: reserva, WhatsApp, formulário ou outro canal de contato.
   - Imagens devem ter propósito, texto alternativo, carregamento otimizado e não comprometer desempenho.
   - Interface deve transmitir hospitalidade, confiança e qualidade, sem sacrificar clareza ou velocidade.

5. SEO, performance e observabilidade
   - Estrutura semântica, metadados, URLs amigáveis e conteúdo indexável.
   - Definir orçamento de performance e priorizar Core Web Vitals.
   - Evitar dependências desnecessárias e assets excessivamente pesados.
   - Preparar pontos de integração para analytics e monitoramento, respeitando privacidade e consentimento.

6. Evolução para SaaS
   - Preservar fronteiras claras entre apresentação, domínio e integração externa.
   - Planejar contratos de dados e tratamento consistente de carregamento, erro e vazio.
   - Não antecipar complexidade de backend, mas evitar decisões que bloqueiem API, autenticação, pagamentos, reservas ou painel administrativo no futuro.

7. Governança
   - Definir como mudanças na constituição são propostas, revisadas, versionadas e verificadas nos planos, especificações e tarefas.
   - Atualizar os templates do Spec Kit conforme necessário.
   - Gere o relatório de impacto/sincronização exigido pela skill.
   
8. Orquestração de capacidades especializadas
   - Definir que a constituição governa critérios de qualidade, e não duplica instruções operacionais de skills.
   - Para páginas públicas, acessibilidade, SEO/performance e QA de frontend são gates obrigatórios antes da entrega.
   - Para criação ou alteração relevante de UI, aplicar as capacidades de UX/UI, conteúdo de conversão e frontend React conforme o escopo.
   - Skills genéricas podem ser reutilizadas globalmente; skills específicas do domínio, marca, APIs ou regras de negócio devem ser versionadas no repositório.
   - MCPs e integrações externas só devem ser introduzidos quando houver uma necessidade concreta, credenciais/autorização e um responsável definido.

Tecnologias:
- React e TypeScript são obrigatórios.
- Recomende e registre uma decisão arquitetural para o framework/build tool mais adequado à landing page, considerando SEO e futura evolução, justificando a escolha.
- Utilize práticas modernas e estáveis; evite escolher ferramentas apenas por moda.

A constituição deve ser objetiva, prescritiva e usar MUST/SHOULD com critérios verificáveis. Não deixe placeholders sem justificativa.

Solicitação para o frontend consumir os endpoints da API + Construção das telas administrativas
/speckit-specify Preciso implementar as telas administrativas que consomem a Guacamayo API
(repositório separado, já pronta e testada — 128 testes passando). Autenticação por login
(JWT + refresh token rotativo). Testar contra a API local por enquanto (http://localhost:5249,
CORS já liberado para http://localhost:3000), trocando só a URL base quando o deploy AWS
estiver pronto.

Escopo:

1. Login persistindo o access/refresh token e renovando automaticamente antes de expirar
   (POST /api/auth/login, POST /api/auth/refresh, POST /api/auth/logout).

2. CRUD completo de Quartos, Espaços de Evento e Depoimentos (/api/admin/rooms,
   /api/admin/event-spaces, /api/admin/testimonials) — formulário multilíngue (pt/en/es),
   listagem, criação, edição respeitando controle de concorrência otimista via campo rowVersion
   (um PUT com rowVersion desatualizado retorna 409, a tela deve pedir pra recarregar), exclusão
   com confirmação.

3. Edição das Configurações do Site (/api/admin/site-settings) — registro único, sem
   criação/exclusão.

4. Gestão de Leads (/api/admin/leads) — os contatos que o bot de WhatsApp captura, hoje
   invisíveis em qualquer tela: (a) listagem paginada (skip/take) com filtro por status
   (Novo/Contatado/Fechado) e por intervalo de data de criação, mais recentes primeiro; (b) tela
   de detalhe de um lead mostrando nome/telefone/interesse/mensagem e o histórico completo de
   mensagens da conversa que o originou (pode vir vazio, é um estado normal, não um erro); (c)
   ação de marcar um lead como "Contatado" ou "Fechado", com o mesmo controle de rowVersion/409
   do item 2.

5. Tratamento de erro genérico a partir do envelope padrão da API ({isSuccess, data, error}) —
   toasts ou mensagens de formulário a partir de error.code/error.message/error.details.

6. Proteção de todas as rotas administrativas exigindo login válido.

Os contratos completos de request/response de cada endpoint estão documentados no repositório da
API em D:/Dev/codex/guacamayo-api/specs/001-admin-auth-whatsapp-bot/contracts/ (auth-api.md, admin-content-api.md) e
D:/Dev/codex/guacamayo-api/specs/003-admin-leads-management/contracts/admin-leads-api.md — usar como fonte da verdade em vez
de adivinhar o formato (nomes de campo, valores de enum como números inteiros, forma exata do
rowVersion como string opaca).
